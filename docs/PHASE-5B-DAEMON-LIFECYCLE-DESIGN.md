# Forgehand Phase 5B — Controlled Daemon Lifecycle Management

Status: design only; no Phase 5B implementation is included with this document.

This document uses **Current** for behavior present in the repository and **Proposed** for Phase 5B behavior. Line references describe the source at the time of this investigation and are included to make the conclusions auditable.

## 1. Current architecture findings

### Current

Forgehand has two materially different control paths:

- The local CLI/TUI talks to the daemon over its Unix socket. The daemon owns the SQLite database, durable queue, dispatcher, and worker goroutines.
- The Avalonia client talks to the daemon's loopback HTTP API using a bearer account session. It does not have local process or systemd access.

The daemon is the only component with a complete, current view of execution admission. `dispatcher` is explicitly the sole daemon-side scheduling loop (`internal/daemon/dispatcher.go:11-26`). On startup and each wake it claims durable queued work and launches workers (`internal/daemon/dispatcher.go:63-80`, `82-125`). The database transaction in `ClaimNextQueuedExecution` changes the selected execution from `QUEUED` to `RUNNING` (`internal/state/queue.go:739-834`). This transaction protects competing claims, but it is not a lifecycle barrier.

The worker registry tracks in-process ownership. A worker is claimed before its goroutine starts and released when it exits (`internal/daemon/daemon.go:1902-2007`); `workerGroup.stopAndWait` prevents new claims, cancels current workers, and joins them (`internal/daemon/daemon.go:229-243`). That stop flag is used only during process shutdown and does not coordinate a pre-restart safety decision with the dispatcher or request handlers.

The daemon starts the dispatcher before accepting local connections and the dispatcher's first action is to drain old queued work (`internal/daemon/daemon.go:428-450`; `internal/daemon/dispatcher.go:63-70`). Therefore queued work is durable, but it is not quiescent: after a restart the replacement daemon will promptly run it.

Phase 5A's operational status is read-only. The status provider is wired into the remote API beside the dispatcher and worker registry (`internal/daemon/daemon.go:452-455`), and the remote route requires an administrator (`internal/remoteapi/server.go:55-113`). The executable comparison on Linux uses file identity and metadata rather than path text alone (`internal/daemon/executable_status_linux.go:14-72`). This is useful evidence for a lifecycle decision, but status polling cannot make that decision atomic.

The Avalonia client keeps the bearer token in its service session and discards stale asynchronous results when a session ends (`client/src/Forgehand.Client.Core/Session/ForgehandService.cs:213-238`). `DaemonStatusViewModel` already provides cancellable, generation-checked manual refresh (`client/src/Forgehand.Client.Core/ViewModels/DaemonStatusViewModel.cs:8-149`), while `ShellViewModel` restricts the operational-status navigation to administrators and clears it on logout/session expiry (`client/src/Forgehand.Client.Core/ViewModels/ShellViewModel.cs:97-98`, `185-240`). Those are appropriate patterns for a lifecycle view, but they do not yet provide step-up authentication or restart coordination.

### Finding

The authority that decides whether a restart is safe must be inside the daemon, adjacent to the admission and dispatch paths. A desktop-only check, a second scheduler, or a database count followed by a systemd command cannot close the race.

## 2. Existing lifecycle and shutdown behavior

### Current

Daemon startup acquires exclusive state-directory ownership, opens SQLite, binds the Unix socket, reconciles orphaned `RUNNING` executions to `INTERRUPTED`, and recovers related work-plan and qualification state (`internal/daemon/daemon.go:317-389`). It records a daemon run after startup (`internal/daemon/daemon.go:401-412`).

The process handles `SIGTERM` and `SIGINT` by cancelling the root context and closing the Unix listener (`internal/daemon/daemon.go:391-399`). Deferred cleanup then stops and joins workers, joins the dispatcher before closing the database, and marks the daemon run as a clean shutdown (`internal/daemon/daemon.go:438-448`). The HTTP server gets a five-second graceful-shutdown attempt (`internal/daemon/daemon.go:459-464`). A cancelled worker persists a still-`RUNNING` execution as `INTERRUPTED`; a worker that already transitioned to `WAITING_FOR_USER` has returned and is not active (`internal/daemon/daemon.go:2290-2385`). `INTERRUPTED` is intentionally durable and resumable (`internal/state/executions.go:547-560`).

The supported user unit is generated by `service.Manager`, not by the system-wide template under `packaging/systemd`. It runs a fixed absolute executable with fixed state and socket environment, uses `KillSignal=SIGTERM`, and has a 90-second stop timeout (`internal/service/service.go:446-479`). `Restart=on-failure` is configured, but an explicit systemd restart is still the required mechanism.

The CLI/TUI currently invokes `service.Manager.Restart`, which runs `systemctl --user restart forgehand.service` and waits for that command (`internal/service/service.go:188-193`, `482-492`). The TUI inspects the daemon and user service, rechecks status and work, then calls the manager and polls for reconnection (`internal/tui/upgrade.go:58-116`, `202-249`). It can also explicitly authorize interruption of active work (`internal/tui/upgrade.go:175-199`), which is incompatible with the conservative Phase 5B remote policy.

### Gap

Between the TUI's final work check and `Manager.Restart`, a local or remote request can enqueue work and the dispatcher can claim it. A blocking `systemctl restart` is also unsuitable when issued by the process systemd is about to stop: the caller can be terminated while waiting for the job it initiated. The current path is useful for a human at the local terminal, but it cannot be exposed remotely as-is.

## 3. Security and authorization analysis

### Current

Remote requests authenticate with a bearer session. The middleware hashes the presented token, reloads the session and account, and rejects expired, revoked, idle, or inactive credentials (`internal/identity/identity.go:502-543`; `internal/remoteapi/server.go:583-618`). Administrator role checks already protect daemon operational status (`internal/remoteapi/server.go:89-113`). The listener is loopback-only and has explicit HTTP timeouts (`internal/daemon/remoteapi.go:18-99`). Non-GET API calls require the exact compatibility header (`internal/remoteapi/server.go:115-129`), and JSON decoding is bounded and strict (`internal/remoteapi/server.go:674-705`).

Login verifies the password with the existing Argon2 verifier, checks account state, validates either TOTP or a recovery code, clears failure state, and creates a session (`internal/identity/identity.go:409-500`). TOTP secrets are decrypted with the state master key and validated against the stored last counter (`internal/identity/identity.go:766-799`). Per-peer login throttling is in memory (`internal/auth/ratelimit.go:9-18`, `40-51`); account failure lockout is persisted with a default threshold of five failures and a 15-minute lock (`internal/identity/identity.go:52-64`). Security policy already requires password plus TOTP, recent reauthentication for sensitive operations, rate limiting, and audit (`docs/SECURITY-PRINCIPLES.md:159-189`, `198-214`).

There is an important existing concurrency limitation: TOTP validation reads `TOTPLastCounter`, and `UpdateAccountTOTPCounter` then performs an unconditional update (`internal/state/accounts.go:447-466`). Two concurrent requests using the same fresh code can both validate before either update commits. Phase 5B must not copy this logic into an endpoint and amplify the replay window.

### Proposed step-up authorization

Add one reusable identity-service operation, conceptually:

```text
AuthorizeSensitiveOperation(principal, password, totpCode, purpose, remoteAddress)
    -> one-time authorization
```

It must:

1. Revalidate the bearer session, active account, and administrator role.
2. Verify the password using the existing password verifier.
3. Require a fresh TOTP code. Recovery codes are deliberately not accepted for remote restart.
4. Atomically consume the TOTP counter. Prefer a conditional database update such as `UPDATE ... WHERE totp_last_counter < ?`, with exactly one successful row, and share that primitive with normal login. Per-account serialization may reduce contention but is not sufficient without the database condition.
5. Apply a restart-specific, tighter throttle (recommended initial policy: five failed step-up attempts per account and per peer in 15 minutes) in addition to existing account lockout.
6. Audit success and every failure without recording a password, TOTP, bearer token, or authorization token. `RecordSessionOperation` and the existing non-secret audit schema are the current extension points (`internal/identity/identity.go:667-686`; `internal/state/accounts.go:886-918`).
7. Mint a cryptographically random, opaque, single-use authorization bound to account ID, account-session ID, purpose `daemon.restart`, and an expiry (recommended: 60 seconds). Store it only in daemon memory; retain only a hash if lookup by token is required.

The bearer session establishes identity and role. The one-time authorization proves recent password plus fresh TOTP. Neither is a substitute for the other.

## 4. Restart safety policy

### Proposed policy

A remote restart is accepted only when all of these conditions are established atomically at confirmation time:

- The caller still has the same valid administrator session that obtained the step-up authorization.
- The authorization is unexpired, purpose-bound, and unused.
- No other restart is preparing, committed, or awaiting replacement verification.
- The daemon lifecycle coordinator, dispatcher, worker registry, and database are healthy enough to answer conclusively.
- Admission has been closed and all admission/dispatch permits acquired before closure have drained.
- Active in-process worker ownership is zero.
- Durable `RUNNING` execution count is zero. A nonzero durable count with zero owners is an uncertain/inconsistent condition and is rejected.
- Durable `QUEUED` execution count is zero.
- `WAITING_FOR_USER` work may exist. It is durable and has no owning worker after `requestHumanInput` returns (`internal/daemon/daemon.go:2316-2355`).
- The running process is conclusively owned by the supported, Forgehand-managed `forgehand.service` user unit.
- The effective unit is configured to launch the intended installed Forgehand executable with the current state directory and socket path.

There is no force flag and no “cancel work and restart” option. Active and queued counts are both hard rejections. Queued work is rejected even though it is durable because the replacement daemon dispatches it immediately on startup; accepting it would make the quiescent boundary misleading and would allow work to begin during the lifecycle transition.

An installed/running executable mismatch reported by Phase 5A is not itself a rejection. Updating the installed binary is a primary reason to restart. The required check is that the effective unit points to the intended installed executable and that the unit owns this process. Failure to read or compare any of this evidence is a rejection, not permission to proceed.

| Observed condition | Decision | Rationale |
| --- | --- | --- |
| No workers, no durable running/queued work, healthy coordinator/database, managed ownership proven | Permit confirmation. | This is the only ordinary idle restart case. |
| One or more queued executions | Reject. | The replacement's initial dispatch would make queued work active immediately. |
| One or more active workers or durable `RUNNING` rows | Reject. | Ordinary restart must not interrupt or orphan work. |
| Only `WAITING_FOR_USER` executions | Permit if every other check passes. | The state is durable and no worker owns it. |
| Dispatcher is starting, stopping, unhealthy, or cannot grant/drain its permit | Reject. | Quiescence cannot be proven. |
| Daemon is already shutting down or lifecycle state is not `RUNNING` | Reject/conflict. | A second transition has no safe ownership semantics. |
| A previous restart is prepared | Reject a different request; allow only idempotent access to the same request and expire it promptly. | This satisfies the single-request policy without closing execution admission during the dialog. |
| A previous restart is committed/enqueued | Reject/conflict and return the existing request's status. | Prevent duplicate service jobs and ambiguous attribution. |
| State database is unavailable or a count query fails | Reject. | In-memory counts alone cannot prove durable execution state. |
| Daemon is manual, unmanaged, or systemd `MainPID` does not identify this process | Reject. | The endpoint must not control an unverified process or unit. |
| Installed executable differs from the running executable | Permit if the intended unit target and every other condition verify. | Installing a new executable is the expected restart use case. |

## 5. Race-condition mitigation

### Proposed coordinator

Add one daemon-owned lifecycle coordinator shared by every operation that can create or claim executable work. It is an admission gate, not a second scheduler.

```text
RUNNING
  | confirm begins; close gate
  v
RESTART_PREPARING -- safety/service check fails --> RUNNING + wake dispatcher
  | all checks pass and authorization consumed
  v
RESTART_COMMITTED / accepted -- manager rejects before enqueue --> RUNNING + wake dispatcher
  | systemd job enqueued
  v
SHUTTING_DOWN -- replacement starts --> REPLACEMENT_VERIFIED
```

Admission and dispatcher rules:

- Local Unix-socket operations and remote HTTP operations that enqueue, resume, or otherwise create runnable execution state must acquire an admission permit before their database transaction and hold it through notification of the dispatcher.
- The dispatcher must acquire a dispatch permit before `ClaimNextQueuedExecution` and hold it through worker ownership/launch. This closes the gap between a zero-count query and a concurrent `QUEUED -> RUNNING` claim.
- Confirmation atomically changes `RUNNING` to `RESTART_PREPARING`, prevents new permits, and waits for prior permits to drain. It then queries durable counts and in-memory owners while the gate remains closed.
- Any database error, unknown dispatcher state, unowned `RUNNING` row, permit-drain timeout, or service-inspection error is fail-closed.
- If confirmation is rejected before the systemd job is enqueued, restore `RUNNING` and notify the dispatcher so work cannot remain stranded.
- Once systemd accepts the restart job, never reopen the gate in the old process. systemd owns the lifecycle from that point.

The preparation endpoint performs authentication and an advisory preflight, but does not close the gate for the token's lifetime. Holding the gate while a user reads a dialog would let an authenticated administrator stall all execution admission for up to the authorization TTL. Confirmation performs the authoritative gated recheck.

Only one global restart request may be outstanding in `prepared` or any later nonterminal state. Authorization consumption and the durable request transition must use compare-and-swap semantics. A repeated confirmation for the same request returns its recorded state; it must never enqueue a second systemd restart. A different concurrent request receives `409 restart_in_progress`. Preparation does not close admission, so the maximum operational effect of an abandoned preparation is a short delay before another restart can be prepared.

## 6. Recommended systemd coordination mechanism

### Current validation to retain and strengthen

`service.Manager.Status` verifies that a unit file exists, contains Forgehand's managed marker, and asks systemd for `ActiveState`, `SubState`, `MainPID`, and `ExecStart` (`internal/service/service.go:213-252`). The TUI additionally requires active `MainPID` to equal the daemon's IPC PID (`internal/tui/upgrade.go:69-74`). The manager executes `systemctl` directly with fixed arguments and no shell (`internal/service/service.go:23-35`, `482-492`).

Before remote restart, extend service inspection to require:

- user unit name exactly `forgehand.service` (`internal/service/service.go:18-21`);
- installed and Forgehand-managed base unit;
- `ActiveState=active` and `MainPID == os.Getpid()`;
- effective `ExecStart` is the expected absolute installed executable plus the fixed `daemon` argument;
- effective state-directory and socket environment match the running daemon;
- no pending daemon reload and no effective drop-in override that changes those values;
- the installed executable can be statted and is the intended replacement target.

The managed marker is provenance evidence, not a security boundary against the same Unix user. That user can edit its own unit and binary and can signal the daemon. Phase 5B prevents unintended remote control and confused-unit errors; it cannot defend the process from its owning OS account.

### Recommended restart mechanism

Add a narrowly scoped service operation that executes exactly:

```text
systemctl --user --no-block restart forgehand.service
```

Use `exec.CommandContext` through the existing runner, a short timeout, fixed arguments, no caller-supplied unit/path/options, and captured output with secret scrubbing. `--no-block` is essential: it returns after systemd verifies and enqueues the job rather than waiting for the daemon's own stop/start job to complete. A successful call means **restart enqueued**, not **replacement verified**.

Do not reuse `Manager.Restart` unchanged. It blocks and `requireCurrentExecutable` compares the running executable path with the unit target (`internal/service/service.go:255-272`, `430-444`), which is the wrong invariant when the file at the installed path has intentionally been replaced.

Alternatives considered:

- **Direct systemd D-Bus `RestartUnit`:** architecturally clean, returns a job object, and can be observed with `JobRemoved`. Race-free observation requires subscribing before the call. It adds a D-Bus dependency and the caller is still stopped before it can reliably report completion. It is a reasonable later enhancement, not required for the first implementation.
- **External privileged/coordinator helper:** could survive the daemon and report final status, but adds a process, packaging, authorization surface, and possibly privilege. It conflicts with Forgehand's no-new-privilege posture and is not justified for a per-user unit.
- **Self-exit and rely on `Restart=on-failure`:** rejected. A clean `SIGTERM`/exit is not a failure restart, and deliberately crashing the daemon would corrupt lifecycle semantics. An explicit systemd restart job is required.

systemd documents `restart` as stop followed by start and `--no-block` as enqueue-without-wait. The user manager is selected by `--user`: [systemctl documentation](https://www.freedesktop.org/software/systemd/man/latest/systemctl.html). `RestartUnit` is asynchronous and job completion requires `JobRemoved` subscription: [systemd D-Bus API](https://www.freedesktop.org/software/systemd/man/latest/org.freedesktop.systemd1.html). Explicit systemd operations are distinct from `Restart=on-failure`: [systemd.service documentation](https://www.freedesktop.org/software/systemd/man/latest/systemd.service.html).

## 7. Proposed HTTP API contract

All endpoints are under `/api/v1`, require the existing bearer session, administrator role, exact compatibility header where applicable, loopback transport, bounded strict JSON, and no caching. Error bodies use stable machine codes and generic human-readable messages; logs and audit events must not contain secrets.

### `POST /api/v1/daemon/restart/prepare`

Request:

```json
{
  "password": "current account password",
  "totp_code": "123456"
}
```

The server performs step-up authorization and an advisory preflight. The client cannot supply a username, unit, executable, state directory, socket, or command.

Successful `201 Created` response:

```json
{
  "request_id": "opaque restart request id",
  "authorization_token": "opaque one-time token",
  "expires_at": "2026-10-25T12:00:00Z",
  "confirm_required": true,
  "preflight": {
    "daemon_instance_id": "current daemon-run identity",
    "active_workers": 0,
    "running_executions": 0,
    "queued_executions": 0,
    "waiting_executions": 2,
    "managed_user_service": true,
    "installed_executable_differs": true
  }
}
```

Preparation does not promise that confirmation will succeed. It does not reserve the scheduler or start a restart.

### `POST /api/v1/daemon/restart/confirm`

Request:

```json
{
  "request_id": "opaque restart request id",
  "authorization_token": "opaque one-time token"
}
```

The server revalidates the same bearer session, consumes the authorization, closes admission, performs the authoritative safety and service-ownership checks, durably commits the request, and enqueues the fixed systemd job.

Successful `202 Accepted` response, if the old daemon remains alive long enough to deliver it:

```json
{
  "request_id": "opaque restart request id",
  "state": "restart_enqueued",
  "old_daemon_instance_id": "daemon run identity before restart",
  "status_url": "/api/v1/daemon/restart/status?request_id=...",
  "retry_after_seconds": 1
}
```

The connection may close without a response because systemd can deliver `SIGTERM` immediately after enqueue. A dropped connection means **outcome unknown**, not failure, and the client must reconnect and query status using the same request ID. It must not submit a new confirmation automatically.

### `GET /api/v1/daemon/restart/status?request_id=...`

The request ID and non-secret lifecycle record are durable; the one-time authorization is not. The replacement daemon reconciles the latest committed request during startup. It marks `replacement_verified` only after observing a new daemon-run/instance identity and verifying that its PID is the managed unit's `MainPID` with the expected effective configuration.

Example response:

```json
{
  "request_id": "opaque restart request id",
  "state": "replacement_verified",
  "requested_at": "2026-10-25T11:59:30Z",
  "old_daemon_instance_id": "old identity",
  "new_daemon_instance_id": "new identity",
  "build_identity": "replacement build identity",
  "verified_at": "2026-10-25T11:59:33Z"
}
```

States have deliberately narrow meanings:

- `prepared`: step-up succeeded; no restart accepted.
- `accepted`: confirmation passed, admission is closed, and the request was durably committed; systemd has not yet accepted a job. This state is normally brief but is necessary to distinguish application acceptance from initiation.
- `restart_enqueued`: the user manager accepted a restart job, so restart was initiated; replacement not yet proven.
- `replacement_verified`: a different daemon instance is running under the expected managed unit.
- `rejected`: no job was enqueued and admission was reopened.
- `failed`: a definitive pre-enqueue manager failure or a definitive startup reconciliation failure is recorded.
- `unknown`: the client timed out without enough evidence. A timeout alone must not be converted to `failed`.

If the daemon crashes in `accepted` before enqueueing a job, its ordinary `Restart=on-failure` policy may start a replacement. On startup, that process must treat the stale accepted record as interrupted preparation, verify that no systemd restart was proven, mark the request `failed` or `unknown` with a specific non-secret reason, and reopen normal admission. It must not enqueue the old request automatically.

Recommended error mapping:

| HTTP | Code | Meaning |
| --- | --- | --- |
| 400 | `invalid_request` | Strict JSON or field validation failed. |
| 401 | `authentication_required` / `step_up_failed` | Bearer or supplied factors are invalid. Keep factor-specific detail private. |
| 403 | `administrator_required` | Authenticated account is not an administrator. |
| 409 | `active_work`, `queued_work`, `restart_in_progress`, `daemon_state_uncertain`, `unmanaged_daemon` | Current state safely rejects restart. Include non-secret counts where relevant. |
| 410 | `authorization_expired` | The one-time authorization expired. A consumed token returns its existing request status rather than starting again. |
| 429 | `step_up_throttled` | Per-account or per-peer sensitive-operation limit reached. |
| 503 | `lifecycle_unavailable`, `database_unavailable`, `service_manager_unavailable` | The daemon cannot establish safety conclusively. |

Audit event types should distinguish `daemon_restart_step_up_succeeded`, `daemon_restart_step_up_failed`, `daemon_restart_rejected`, `daemon_restart_accepted`, `daemon_restart_enqueued`, `daemon_restart_replacement_verified`, and `daemon_restart_failed`. Record request ID, attributable account/session IDs, remote address, timestamps, counts, and non-secret reason codes as applicable. Never record submitted factors, bearer/authorization tokens, or raw request bodies.

## 8. Proposed Avalonia workflow

### Proposed

Add lifecycle controls to the administrator-only daemon status surface, reusing its refresh/cancellation/session-generation patterns rather than placing restart on a general project view.

1. Show restart only when authenticated as administrator. Display current daemon build, installed executable comparison, active/running/queued/waiting counts, and managed-service status.
2. “Restart daemon” opens a modal step-up form for password and TOTP. Do not retain either field after the prepare request completes. Disable paste/history only if the platform already has a consistent sensitive-entry policy; do not invent a custom clipboard subsystem.
3. After `prepare`, show a confirmation dialog with the fresh preflight snapshot, explain that confirmation is rechecked and may be rejected, and state that active or queued work cannot be overridden.
4. On confirm, disable duplicate submission and retain the request ID in view-model state. Treat `202`, connection loss, timeout, and transport cancellation as “verification pending” until polling resolves them.
5. Expect the HTTP connection to disappear. Reconnect with bounded exponential backoff, perform the ordinary compatibility/authenticated health flow, and query the request status. Do not resend credentials or confirmation automatically.
6. Declare success only for `replacement_verified`. Show “restart accepted; waiting for replacement” for `restart_enqueued`. On timeout show “replacement not verified” with manual Retry Status and service-recovery guidance; do not claim failure.
7. If the persisted account session remains valid, reuse it after reconnect. If the replacement returns `401`, stop polling, request normal login, and then allow the administrator to query the saved request ID. Never cache the password or TOTP to reauthenticate.
8. Closing the dialog or application does not cancel a committed restart. Reopening the daemon status view may query the last request ID for the current account session.

Keyboard navigation, ordinary mouse activation, focus restoration, cancellation, screen-reader labels, and masked password entry must follow existing Avalonia patterns. No client code may invoke `systemctl` or accept a unit/executable argument.

## 9. Failure and recovery handling

| Failure point | Required behavior |
| --- | --- |
| Bearer, role, password, TOTP, throttle, or audit precondition fails | Do not close admission or create a usable authorization. Return a generic error and audit the outcome. |
| Prepared authorization expires or UI is abandoned | Delete/expire the in-memory authorization. No scheduler state changes. |
| Admission permits do not drain or safety query is ambiguous | Reject, reopen admission, wake dispatcher, and preserve the durable request as rejected. |
| Daemon crashes during preparation before durable acceptance | In-memory authorization disappears; ordinary startup resumes normal admission. No restart is inferred. |
| Daemon crashes after durable acceptance but before systemd enqueue is proven | Startup reconciles the stale request to failed/unknown and does not replay it. If `Restart=on-failure` started the process, that is crash recovery, not proof that the requested restart was initiated. |
| Managed-unit ownership/configuration check fails | Reject before invoking systemd. Manual/unmanaged daemons remain manual operations. |
| `systemctl --no-block` returns a definite error | Record failure, reopen admission, wake dispatcher, and return a sanitized `503`. |
| Job is enqueued but HTTP response is lost | Keep the durable request as `restart_enqueued`; client reconnects and queries it. Never infer that a lost response means no restart. |
| Old daemon receives `SIGTERM` | Existing graceful shutdown cancels workers (none are permitted by policy), joins dispatcher, shuts down HTTP, and records clean shutdown. |
| Replacement starts | Existing startup reconciliation runs, then lifecycle reconciliation verifies new instance plus systemd ownership before marking success. |
| Replacement cannot start | HTTP is unavailable. Desktop times out to `unknown`, preserves the request ID, and presents local `forgehand service status` / journal recovery guidance. It must not loop restart requests. |
| Replacement starts but session is invalid | Client prompts for normal login, then allows status lookup. The restart itself is not repeated. |
| Desktop exits after confirmation | systemd continues independently; durable request state permits later inspection. |

Persist no password, TOTP, bearer token, or one-time authorization. A lifecycle record needs only request ID, requesting account/session identifiers as appropriate, timestamps, non-secret result/error code, old/new daemon instance IDs, and build/service evidence required for audit and reconciliation. Define a retention policy and prune old records.

## 10. Threat model

| Threat | Control | Residual limitation |
| --- | --- | --- |
| Stolen bearer token triggers restart | Administrator role plus recent password and fresh TOTP step-up; short-lived purpose/session-bound authorization. | An attacker holding all factors during the window can act as the administrator. |
| Ordinary project user requests restart | Daemon-side administrator check on prepare, confirm, and status; authorization is not inferred from project access. | A wrongly assigned administrator role remains an account-provisioning risk. |
| Replay of TOTP or authorization token | Atomic TOTP-counter consume; random single-use authorization; confirm compare-and-swap; idempotent request ID. | Clock/TOTP configuration remains account security infrastructure. |
| Brute-force step-up | Per-peer and per-account sensitive-operation throttle, existing persistent lockout, generic failures, audit. | In-memory peer limits reset with daemon restart; persisted account lock remains the durable backstop. |
| Work begins between check and restart | Shared admission/dispatch permits; gate closure and permit drain before counts; gate remains closed after enqueue. | Every current and future queue-producing path must use the coordinator; omission is a correctness vulnerability. |
| Execution submission is committing while restart prepares | The database transaction is inside an admission permit; confirmation waits for that permit, then observes either the committed queue row and rejects or no row. | A future producer that omits the permit reintroduces the race. |
| Active work is interrupted | Hard rejection for owners or durable `RUNNING` rows; no force path. | OS shutdown, crash, or local user signals can still interrupt work outside this feature. |
| Queued work starts after restart | Hard rejection for durable queued rows. | Waiting-for-user work is intentionally retained and can later be resumed by a user. |
| Remote caller chooses a command/unit/path | API has no such fields; service layer uses fixed executable invocation, options, and unit. | The owning Unix user can alter its own unit/binary outside Forgehand. |
| Confused deputy restarts another daemon | Require managed user unit, active `MainPID == os.Getpid()`, expected effective configuration and state/socket identity. | PID alone can be reused; verification must also use daemon-run/instance identity and unit evidence. |
| CSRF or browser-origin misuse | Bearer header, non-GET compatibility header, loopback binding, strict methods/content type; do not add cookie authentication. | Malware running as the same desktop user is outside the remote API's strongest boundary. |
| Secret disclosure in logs/audit/UI | Strict redaction and non-secret event detail; sensitive fields cleared immediately; no request-body logging. | Crash dumps/process memory can contain transient secrets; minimize lifetime. |
| Restart-request denial of service | Preparation does not close admission; short authorization TTL; one global commit; throttling. | A legitimate administrator can repeatedly request safe restarts; audit makes this attributable. |
| Malicious, downgraded, or incompatible replacement | Effective unit and installed-file inspection before restart; existing compatibility negotiation and build identity after restart; replacement verification reports actual build. | systemd launches what the user unit names; Phase 5B does not implement signed binaries or protect against the owning Unix user. |
| Different local unprivileged user interferes | Per-user systemd manager, owner-only state/socket permissions, and existing state ownership lock. | Host compromise, permissive filesystem configuration, or access as the service account defeats this boundary. |
| Same-user unit tampering/drop-ins | Inspect effective systemd properties, not only base file; fail closed on mismatch or daemon-reload pending. | Same-user compromise is effectively daemon compromise and cannot be fully mitigated in-process. |

## 11. Testing strategy

No test should restart the developer's real `forgehand.service`. Unit and ordinary integration tests use injected runners, clocks, token sources, service inspectors, and a temporary state directory.

### Go unit tests

- Lifecycle state transitions, permit draining, rollback, dispatcher wake, and “gate remains closed after enqueue.”
- Deterministic race tests that pause enqueue and dispatch on either side of permit acquisition while confirmation runs; prove no `QUEUED -> RUNNING` claim or new queue commit crosses an accepted restart boundary.
- Active-owner, durable-running, queued, waiting-only, ambiguous database, unhealthy dispatcher, and permit-timeout cases.
- Parallel confirmations: exactly one compare-and-swap and exactly one runner call; repeats for the same request are idempotent.
- Fixed service invocation: exact `systemctl --user --no-block restart forgehand.service`; reject injected unit/path/options and invalid ownership/effective configuration.
- Definite command failure rolls back; successful enqueue does not claim replacement success.
- Step-up role/session binding, expiry, purpose binding, password/TOTP failures, throttle, audit redaction, and authorization single use.
- A concurrent same-code TOTP test proving the conditional counter update admits exactly one request.
- API method, content-type, compatibility, strict JSON, body limit, stable status/code mapping, and secret-free responses/logs.
- Startup reconciliation with a new daemon instance, same-instance rejection, PID reuse, stale requests, and pruning.

Run race-enabled Go tests for the coordinator and remote API (`go test -race` on the relevant packages) in addition to the repository's standard Go suite.

### Avalonia headless tests

- Restart action is administrator-only and disabled/rejected for unsafe snapshots.
- Password/TOTP fields are cleared after prepare success, failure, cancellation, logout, and view disposal.
- Confirmation shows counts and cannot override active/queued work.
- Mouse and keyboard activation each issue one prepare/confirm request; double-click/rapid activation cannot duplicate confirmation.
- `202`, disconnect-before-response, timeout, replacement verification, definitive rejection, and `401` after reconnect produce distinct UI states.
- Polling is bounded/cancellable and stale completions cannot update a new login session.
- Closing/reopening can resume status lookup without retaining factors.
- Existing project/session/run/history/status interactions continue to work.

### Opt-in user-systemd integration tests

Run only in an isolated test account or disposable VM with explicit operator approval. Use a separately compiled test harness and test-specific fixed unit wired by dependency injection; never parameterize the production endpoint. Verify explicitly that:

1. active workers reject restart;
2. queued executions reject restart;
3. an idle daemon can commit and enqueue restart;
4. the old daemon exits through its normal `SIGTERM` cleanup;
5. a replacement daemon starts under the user unit;
6. the replacement uses the installed executable;
7. existing SQLite state survives;
8. no execution is duplicated or lost; and
9. the desktop recognizes and verifies the replacement daemon.

Also cover unit failure, durable status reconciliation, and response-loss behavior. Destructive restart tests are excluded from normal CI and from this design task.

## 12. Implementation milestones

1. **Identity foundation:** implement atomic TOTP-counter consumption, shared sensitive-operation step-up, throttle, redacted audit events, and one-time authorization storage.
2. **Lifecycle coordinator:** inventory every enqueue/resume/claim path, add shared admission/dispatch permits, durable safety queries, state transitions, and race tests. Do not expose an endpoint until the inventory is complete.
3. **Service ownership and enqueue:** strengthen effective user-unit inspection and add the fixed non-blocking restart operation with injected-runner tests.
4. **Durable request state and startup reconciliation:** add request persistence, daemon instance identity, idempotent transitions, replacement verification, retention, and failure recovery.
5. **Remote API:** add prepare, confirm, and status endpoints with compatibility/auth/role enforcement and stable errors.
6. **Avalonia workflow:** implement step-up, confirmation, reconnect/status polling, accessibility, session-expiry handling, and headless tests.
7. **Verification and documentation:** run full Go/client tests, race tests, Release build, threat-model review, and manual non-destructive UI validation. Run isolated systemd integration only with explicit authorization.

Each milestone should remain separately reviewable. The remote confirm route must not ship before the coordinator, atomic TOTP consume, effective-unit validation, durable idempotency, and recovery tests are in place.

## 13. Open questions and unresolved risks

1. **Response delivery race:** even non-blocking `systemctl` can cause immediate `SIGTERM` before HTTP flush. The API intentionally makes reconnect/status authoritative. Direct D-Bus cannot eliminate the process-lifetime race; a separate helper could, but is not recommended.
2. **systemctl versus D-Bus:** fixed `systemctl --no-block` is the smallest extension of current code. D-Bus offers job identifiers and signals but adds dependency and lifecycle complexity. Revisit only if job-level diagnostics materially improve supportability.
3. **Durable schema shape:** lifecycle persistence requires a migration and retention policy. It must not retain secrets, but it must retain enough non-secret identity to make retries and audits meaningful.
4. **Complete admission inventory:** executions are not the only possible producers of runnable work. Qualification and work-plan recovery/queue paths must be audited. Missing one path invalidates the atomic safety guarantee.
5. **Daemon instance identity:** build, PID, and start time are not independently collision-proof. Reuse the durable daemon-run ID and/or add a random per-start instance UUID exposed by status.
6. **Effective unit inspection:** current status examines only a limited set of systemd properties and path equality. Exact properties for environment, drop-ins, fragment identity, reload state, and installed-file identity need a Linux/systemd implementation and tests.
7. **Session continuity:** account sessions are persisted, but the client must tolerate expiry/revocation during restart. Reauthentication must never repeat confirmation automatically.
8. **TOTP concurrency is broader than restart:** fixing the counter only in a restart-specific path would leave login semantics inconsistent. The shared identity implementation should receive the atomic fix and regression coverage.
9. **Unreachable failed replacement:** if the new daemon never starts, the HTTP API cannot report definitive failure. The desktop can only time out to `unknown` and direct the administrator to local systemd/journal diagnostics unless an external coordinator is later introduced.
10. **Platform scope:** lifecycle control is Linux user-systemd functionality. The API and Avalonia client need an explicit unsupported response/state on other platforms rather than hidden or partially functioning controls.
11. **Local TUI policy:** the existing TUI can confirm interruption of active work. Phase 5B should either route all restart entry points through the conservative coordinator or clearly retain the local path as a separately documented break-glass behavior. Two contradictory safety policies would be confusing and difficult to test.
12. **Same-user trust boundary:** the user service, daemon, state, and desktop client all run as the same OS user. This design provides application authentication, intent confirmation, race safety, and auditability; it is not privilege separation.

The recommended implementation is intentionally narrow: no backend scheduler redesign, no privileged service, no arbitrary process control, and no automatic cancellation or retry of work. Its central invariant is that only the daemon can close its own admission boundary, prove quiescence, and ask its already-trusted user service manager to replace it.
